## 1. Процесс разработки по шагам

### Шаг 1. Подготовка ТЗ
Взял готовое ТЗ из ДЗ 3 (`technical_specification.md`). Зафиксировал стек: React 18 + TypeScript (strict), Vite, Tailwind CSS, Vitest + RTL. Стек выбран не с нуля, а под правила из `.cursorrules` (ДЗ 2), где он уже закреплён, — так система правил из прошлого задания реально применяется здесь.

Три основные функции из ТЗ, вынесенные в MVP:
1. Расчёт дневной нормы КБЖУ (F1).
2. Дневник питания с подсчётом за день (F2).
3. Поиск продуктов и выбор порции (F3).
Плюс сводка дня (F4) как связующий экран.

### Шаг 2. Инициализация проекта
Проект развёрнут на Vite вручную (без интерактивного `create-vite`, чтобы контролировать структуру): `package.json`, `vite.config.ts`, `tsconfig.json`, `tailwind.config.js`, `postcss.config.js`. Токены дизайна (цвета `bg/ink/brand/macroP…`) вынесены в `tailwind.config.js` — как требует правило 11 из `.cursorrules` (никаких сырых hex в JSX).

### Шаг 3. Базовая структура
Заложена структура Feature-Sliced Design (правило 5 из `.cursorrules`): `entities → features → pages → shared`. Сначала — предметный слой без UI (`entities/`), затем фичи и страницы. Роутинг в MVP тривиальный (онбординг ↔ дневник) и решён условием в `App.tsx` без роутер-библиотеки — лишняя зависимость запрещена правилом 14.

### Шаг 4. Компоненты интерфейса
Компоненты собраны по выбранной в ДЗ 3 концепции A (минимализм): кольцо калорий, бары БЖУ, список приёмов пищи, модалка поиска. Для каждого проработаны состояния: пустой день, пустой поиск, ошибка ввода, превышение нормы. Данные на время разработки — mock-база продуктов в `entities/product/products.ts`.

### Шаг 5. Тестирование и отладка
Написан 21 тест (Vitest + RTL): чистая логика (`calc`, `products`) и компоненты (`Onboarding`, `DiaryPage`). Тесты покрывают позитивные сценарии и обработку ошибок. Отладка описана в разделе 3.

### Шаг 6. Адаптивная вёрстка
Mobile-first: контент в колонке `max-w-md`, модалка поиска — bottom sheet на мобильном и центрированное окно на десктопе (`items-end sm:items-center`, `rounded-t-3xl sm:rounded-3xl`). Проверено от 360 px.

### Шаг 7. Оптимизация и рефакторинг
Вся арифметика вынесена из компонентов в чистые функции (`calc.ts`, `products.ts`, `diary.ts`) — их легко тестировать и переиспользовать. Состояние собрано в один хук `useAppStore`. Это соответствует правилу «деньги/расчёты не в UI» из `.cursorrules` (здесь — КБЖУ вместо денег, принцип тот же).

### Шаг 8. Оформление
README с инструкциями запуска, комментарии к неочевидным местам (формула, безопасный минимум), этот отчёт.

## 2. Применённые техники работы с AI

- **Системные правила как контекст.** В основе — файл `.cursorrules` из ДЗ 2. Он задаёт стек, архитектуру, запреты (`any`, лишние зависимости, хардкод) и формат ответа. За счёт этого сгенерированный код сразу ложился в проект.
- **Промпт-шаблоны RTCF из ДЗ 2.** Генерация компонентов шла по шаблону «Генерация компонента», тесты — по шаблону «Написание тестов», разбор багов — по шаблону «Исправление ошибок».
- **Слои сверху вниз.** Сначала генерировал предметную логику и типы, потом — UI поверх готовых сигнатур. Это уменьшало домысливание агентом контрактов.
- **Мультимодальная отладка.** Ошибки из консоли и вывод тестов передавались агенту как контекст для точечной правки (см. раздел 3).

## 3. Примеры промптов и результатов

### Промпт 1 — генерация чистой логики (по шаблону RTCF)
```
ROLE: Senior Frontend Engineer, правила .cursorrules действуют.
TASK: реализуй чистую функцию расчёта дневной нормы КБЖУ по Миффлину–Сан Жеору
с учётом активности и цели. Норма не ниже безопасного минимума, факт
ограничения — флагом.
CONTEXT: типы UserParams/DailyNorm; коэффициенты активности 1.2–1.9;
цель: похудение −15%, поддержание 0%, набор +10%; макросы 30/30/40.
FORMAT: чистая функция + тесты happy-path и край.
```
**Результат:** `calc.ts` с `calcBmr`, `calcDailyNorm`, `validateParams` и тестами. Ключевое решение — вернуть `cappedToSafeMinimum` флагом, чтобы UI показал предупреждение, а не молча занизил цель.

### Промпт 2 — генерация компонента
```
ROLE: тот же. TASK: модалка поиска продукта с выбором порции в граммах,
предпросмотром КБЖУ и добавлением в приём пищи. CONTEXT: searchProducts,
nutrientsForPortion; состояния — пустой поиск, порция ≤ 0. FORMAT: план,
код по файлам, data-testid, риски.
```
**Результат:** `FoodSearch.tsx`. Агент сам добавил блокировку кнопки при некорректной порции и пустое состояние поиска — сработали правила формата.

### Промпт 3 — отладка по выводу теста (мультимодальная техника)
```
Тест DiaryPage падает: ожидал "Осталось 1794 ккал", получил
"Осталось NaN ккал". Вот компонент [код] и тест [код]. Найди причину.
```
**Результат:** причина — суммирование по пустому массиву без начального значения; исправлено на явный аккумулятор в `sumNutrients`. Регрессию закрыл тест на превышение нормы.

## 4. Проблемы и решения

| Проблема | Решение |
|---|---|
| Отрицательный «остаток» при превышении нормы | Разделил отображение: при `consumed > target` показывается «Превышение на N ккал», остаток не уходит в минус. Закрыто тестом. |
| Накопление ошибок float при суммировании БЖУ | Округление до 0.1 г на каждом шаге агрегации в `sumNutrients`; тест сверяет калории из макросов с нормой в пределах 3%. |
| Хардкод цветов в компонентах (нарушение правила 11) | Все цвета вынесены в токены `tailwind.config.js` (`brand`, `macroP/F/C`), в JSX только классы/переменные. |
| Мигание/потеря данных между сессиями | Единый хук `useAppStore` с персистом в localStorage и защитой от исключений при чтении/записи. |
| Риск лишних зависимостей (роутер, uuid, axios) | Роутинг — условием в `App.tsx`; id — через `crypto.randomUUID()` с фолбэком; сеть в MVP не нужна (mock-данные). Ноль сторонних runtime-зависимостей сверх React. |

## 5. Наиболее эффективные техники

1. **Файл правил `.cursorrules` как постоянный контекст** — сильнее всего повлиял на качество: код почти не приходилось переписывать под стиль и архитектуру.
2. **Генерация логики отдельно от UI** — чистые функции проще тестировать, и агент реже домысливал контракты.
3. **Отладка через передачу вывода тестов агенту** — точечные правки вместо переписывания; каждая пойманная ошибка сразу закрывалась регрессионным тестом.

## 6. Выводы и рекомендации

Связка «системные правила + RTCF-шаблоны + генерация слоями» дала предсказуемый результат: приложение собирается без ошибок типов, 21 тест зелёный, три основные функции из ТЗ работают. Главный урок — **вкладываться в контекст до генерации** (правила, типы, контракты) выгоднее, чем чинить результат после. Для следующих итераций: подключить реальный API продуктов вместо mock, добавить недельную аналитику (F4 из ТЗ) и e2e-тесты (Playwright) на сквозной сценарий «онбординг → добавление → сводка».
