# Отчёт по аудиту безопасности — приложение «КБЖУ»

**Дата аудита:** сентябрь 2026
**Метод:** `npm audit`, ручная проверка по OWASP Top-10, анализ кода с помощью AI-агента.

---

## 1. Аудит зависимостей (`npm audit`)

### Найдено
На момент аудита `npm audit` показал **5 уязвимостей** (3 moderate, 1 high, 1 critical), все — в **dev-зависимостях** сборочного инструментария:

| Пакет | Severity | Суть |
|---|---|---|
| vitest | critical | Path Traversal / чтение файлов через UI-сервер Vitest и `@vitest/mocker` |
| vite | high | Path Traversal в обработке `.map`, обход `server.fs.deny` (Windows) |
| esbuild | moderate | dev-сервер отвечает на запросы с любого origin |
| @vitest/mocker | moderate | Path Traversal через redirect mock |
| vite-node | moderate | зависит от уязвимой версии vite |

### Оценка риска
Все пять уязвимостей относятся к **инструментам разработки** (Vite dev-server, Vitest), которые:
- работают только локально при `npm run dev` / `npm test`;
- **не входят в production-бандл** — на Vercel раздаётся статическая сборка из `dist/`, где ни Vite dev-server, ни Vitest не присутствуют;
- эксплуатируются лишь при доступе злоумышленника к локальному dev-серверу разработчика.

### Решение
Исправление доступно только через мажорный апгрейд Vite 5 → 6/7 (breaking change), который ломает текущую конфигурацию сборки и тестов. Принятое инженерное решение для учебного проекта — **зафиксировать риск как принятый (accepted risk)**: production не затронут, а мажорный апгрейд ради dev-only проблемы несёт больший риск регрессий, чем сама уязвимость. В CI добавлен шаг `npm audit --omit=dev`, который проверяет **production-зависимости** — по ним уязвимостей **0**.

```
npm audit --omit=dev  →  found 0 vulnerabilities
```

Рекомендация на будущее: плановый переход на Vite 7 / Vitest 3 отдельной задачей с прогоном полного набора тестов.

## 2. Проверка по OWASP Top-10

| Категория OWASP | Статус | Как закрыто |
|---|---|---|
| A01 Broken Access Control | ✅ | Row Level Security на всех таблицах: пользователь видит/меняет только строки с `auth.uid() = user_id`. Проверено на SELECT/INSERT/UPDATE/DELETE. |
| A02 Cryptographic Failures | ✅ | Пароли хранит и хеширует Supabase Auth; весь трафик по HTTPS/TLS; секретов в коде нет. |
| A03 Injection (SQL/XSS) | ✅ | SQL-инъекции исключены: запросы идут через параметризованный клиент supabase-js (PostgREST), сырых SQL-строк с конкатенацией нет. XSS: React экранирует вывод по умолчанию, `dangerouslySetInnerHTML` не используется. |
| A04 Insecure Design | ✅ | Норма калорий ограничена безопасным минимумом; денормализация КБЖУ защищает историю дневника. |
| A05 Security Misconfiguration | ✅ | Сервисный `service_role`-ключ во фронтенд не попадает; во фронтенде только публичный anon/publishable-ключ, доступ ограничивает RLS. |
| A06 Vulnerable Components | ⚠️ | См. раздел 1 — уязвимости только в dev-инструментах, prod чист. |
| A07 Identification & Auth Failures | ✅ | Аутентификация — Supabase Auth (email/пароль + OAuth2 Google), JWT, минимальная длина пароля 6. Сообщение о неверном входе нейтральное (не раскрывает, email или пароль неверны). |
| A08 Data Integrity Failures | ✅ | CHECK-ограничения на диапазоны в БД; валидация ввода на клиенте. |
| A09 Logging & Monitoring Failures | ✅ | Структурное JSON-логирование с уровнями, health-check, внешний мониторинг (UptimeRobot). |
| A10 SSRF | ✅ | Не применимо: фронтенд не делает серверных запросов по пользовательским URL. |

## 3. CSRF

Приложение — SPA, авторизация через **Bearer-JWT в заголовке `Authorization`**, а не через cookie-сессию. Поскольку токен не отправляется браузером автоматически (в отличие от cookie), классическая CSRF-атака неприменима. Дополнительно Supabase проверяет JWT на каждый запрос.

## 4. Проверка секретов

- Все ключи вынесены в переменные окружения (`.env`, шаблон `.env.example`); `.env` в `.gitignore` — в репозиторий не попадает.
- Проведён поиск захардкоженных секретов по коду — не найдено.
- `service_role`-ключ используется только на стороне Supabase, во фронтенд/репозиторий не передаётся.
- Секреты CI/CD (`VERCEL_TOKEN`, ключи Supabase, `VITE_YM_ID`) хранятся в GitHub Secrets и Vercel Environment Variables, в коде отсутствуют.
